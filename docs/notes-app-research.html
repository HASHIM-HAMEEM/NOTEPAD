Notes app for Arabic and English study: research and recommended design

Recommendation in one paragraph

Build a native Android app in Kotlin + Jetpack Compose, with the pen surface on Google's Jetpack Ink API (androidx.ink 1.0.0, stable, C++ core, front-buffer low-latency rendering + motion prediction). Store every note as vector strokes in SQLite, never as pixels. Render PDFs with PDFium (the engine inside Chrome) and write ink back as real PDF ink annotations. Recognise Arabic/Urdu/English handwriting on-device with ML Kit Digital Ink (models ar, ur, en), and OCR scanned PDFs through a swappable cloud/self-hosted engine. Sync via a local-first SQLite replica (PowerSync over Postgres, or an equivalent) with client-side end-to-end encryption, and large files in S3-compatible object storage (Cloudflare R2). Ship a deliberately small MVP: notebooks, pen, PDF annotation, sync, export. Everything else waits.

Why native, not Flutter (your existing stack). Flutter exposes stylus pressure, tilt and orientation, but has no front-buffered rendering path and cannot call the Jetpack Ink API without a platform view. Saber — the best Flutter handwriting app (4.9k stars) — still draws through Skia/Impeller on the normal frame pipeline. For a pen-first app on a 144 Hz tablet, "no issues at all" means the ink must bypass that pipeline, which only the native Android stack does today. Cost: UI code is not shared with your Flutter apps and the app is Android-only (your two devices are both Android).

What the app is — and is not

One north-star workflow: in class, open the textbook PDF, write on it with the pen in Arabic or English, and have the same page — strokes included — on the phone when you leave the room.

Hand-picked feature set (MVP)

  • Notebooks → pages; a page is blank, lined, grid, or a PDF page.
  • Pen, highlighter, eraser (stroke + pixel), lasso select/move/resize, undo/redo.
  • Import a PDF as a notebook; write directly on pages; add blank pages between PDF pages.
  • Typed text blocks with correct Arabic/Urdu shaping and RTL, mixed with ink.
  • Search across typed text, PDF text layer, and recognised handwriting.
  • Sync between phone and tablet, offline-first, encrypted before upload.
  • Export: flattened PDF (ink burned in) and a lossless native bundle; import both.
  • Light/dark/sepia themes, system-colour accent, true-black dark for OLED phone.

Deliberately not built (at least initially)

  • Real-time multi-user collaboration (CRDT complexity, no student need).
  • Block editor / database views / kanban (Notion-style bloat).
  • AI chat, summaries, flashcards — later, behind a single "Ask" action, if ever.
  • Audio recording synced to strokes (Xournal++ has it; adds storage + privacy cost).
  • Web or iOS clients. Keep the data format open so they can come later.
  • Shape recognition, math conversion, infinite canvas.

Inking pipeline (native)

  1. MotionEvent with batched historical points → pressure, tilt, orientation, hover; tool type distinguishes pen, eraser end, finger (palm rejection free).
  2. MotionEventPredictor adds predicted points to hide the last ~1–2 frames of latency.
  3. InProgressStrokesView (ink-authoring) draws the wet stroke on a front buffer, outside the Compose frame cycle.
  4. On lift, the finished Stroke (BrushFamily + StrokeInputBatch) is committed to the page model and re-rendered by CanvasStrokeRenderer.
  5. Persist with ink-storage (StrokeInputBatchSerialization, BrushFamilySerialization) — compact protobuf, exactly what sync and export read back.

Stroke data model

Store inputs, not outlines: per point x, y, t, pressure, tilt, orientation in page coordinates (PDF points, origin at the page corner — never screen pixels), plus a brush reference (family, size, colour, epsilon). This is what Xournal++ (per-point widths), Saber (.sbn2) and Google Ink all do; it keeps undo, lasso transforms, recognition, re-rendering at any zoom and export lossless. Batch strokes per page into one row (~20–100 KB) so sync moves pages, not thousands of tiny items.

Stylus interactions worth getting exactly right

  • Pen writes, finger scrolls/zooms (toggleable); two-finger tap = undo.
  • Eraser end of pen → eraser; pen button → lasso or previous tool (user choice).
  • Hover cursor preview of brush size; palm rejection via tool type, never via "ignore touches while pen is near" hacks alone.
  • Straight-line hold, ruler, and zoom-box writing (write large in a strip, placed small on the page — crucial for dense Arabic marginalia).
  • Stroke eraser vs. pixel eraser; snap-to-text highlighter over PDF text layer.
  • Register the Android Notes role so the pen button / lock-screen note shortcut opens your app.

Design rule: ink on a PDF page lives in your stroke model (editable, synced, recognised), and is projected into PDF ink annotations only on export. Importing an annotated PDF reads existing annotations back as read-only layers. Pages render as 256–512 px tiles with an LRU cache; textbooks of 500+ pages must open instantly, so index page sizes and the text layer lazily and cache them in SQLite.

Decision tree

  1. Handwritten with the pen → ML Kit Digital Ink, per page, in the background after the pen lifts; store text + bounding boxes per stroke group for search and "convert to text". Language = page language (ar / ur / en), auto-switchable per stroke group later.
  2. PDF with a text layer → no OCR. Extract via PDFium (FPDFText), store in FTS5 with per-page offsets for highlight-to-text snapping. Most English PDFs and many modern Arabic ones land here.
  3. Scanned PDF / photo, printed Arabic → a pluggable OcrProvider: default Azure Read (best verified Arabic coverage including handwriting) or Mistral OCR (cheapest); self-hosted PaddleOCR when privacy or cost matters. Run per page on demand, cache result with the asset.
  4. Scanned Arabic handwriting (old manuscripts, friends' notes) → Azure Read or Gemini vision; label results "approximate".
  5. Never upload a page for OCR without an explicit tap; E2EE is otherwise meaningless.
Validation needed before committing. Run 20 pages each of (a) printed Arabic textbook, (b) Urdu nastaʿlīq, (c) your own handwriting, through ML Kit Digital Ink, Azure Read, Mistral OCR and PaddleOCR, and score character error rate. Nastaʿlīq in particular is weak in most engines; expect to tell users Urdu OCR is "beta".

Encryption and keys

  • Account key derived with Argon2id from a passphrase; a printable recovery key shown once (Notesnook pattern). No passphrase → no data; say so plainly.
  • Per-notebook content keys wrapped by the account key, so sharing a notebook later doesn't expose everything.
  • Encrypt stroke batches, text, recognition results and blobs with XChaCha20-Poly1305. Leave ids, timestamps, sizes, and page order in plaintext so sync rules and ordering work.
  • Search stays on-device (FTS over decrypted rows) — the server never gets an index.
  • Device enrolment: second device scans a QR code shown by the first (key exchange over the server, encrypted to the new device's public key) rather than retyping the passphrase.

Interface: minimal, tablet-first, bilingual

Structure

  • Tablet: two-pane. Left rail (Notebooks · Recent · Search · Settings), content pane. In a page, the rail collapses to a 40 px strip; one floating pen toolbar, pinnable to any edge, auto-hides while writing.
  • Phone: single pane, bottom bar with three items (Notebooks · Search · Recent). Pages open in a read-first viewer; writing is allowed but secondary.
  • Notebook = a cover + list of pages; no folders deeper than Notebook → Section. Tags instead of hierarchy.
  • Page thumbnails grid for navigation inside long textbooks; bookmarks; outline from the PDF.
  • Settings fit on one screen. If a feature needs a settings page, question the feature.

Arabic / Urdu / English rules

  • Text blocks auto-detect direction per paragraph; Arabic/Urdu stay RTL and right-aligned even when the app UI is English (your standing rule).
  • Fonts bundled: Noto Naskh Arabic (Arabic), Noto Nastaliq Urdu (Urdu), Inter or Noto Sans (English). Line height for nastaʿlīq ≥ 1.8.
  • Page templates include RTL-lined pages (margin on the right) and a Quran/hadith wide-margin template.
  • Handwriting recognition language is a page property with a one-tap toggle in the toolbar.
  • Full UI mirroring when app language is Arabic/Urdu (Compose LayoutDirection.Rtl) — including the pen toolbar and lasso handles.

Themes

Three themes only — light, dark (true black on the phone, dark grey on the tablet LCD), and sepia for reading — plus system accent colour (Material You) with a fixed fallback. Paper colour is a per-notebook property independent of the UI theme, so a dark UI can still show cream paper. Contrast ≥ 4.5:1 for all labels in every theme (a past failure point). No gradients, no cards-in-cards, no onboarding carousel.
